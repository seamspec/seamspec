# Version 0.1.0 in the code, a changelog, and install docs for the published package

## Context

Release step 5 (agreed 2026-10-23) prepares the first release without publishing it. Until now the package was `0.1.0.dev0` and the plugin `0.1.0-dev`. The README and getting-started told readers to install from a clone, because `uv tool install seamspec` gets the empty placeholder on PyPI (0.0.1 to 0.0.3). The README's links were relative, which works on GitHub but leads nowhere on pypi.org, where the README is shown on its own. The plugin's start script still said "Before the release, install your checkout".

The version decides behavior, not only a label: a released version writes a CI workflow that installs `seamspec==<version>`, offers that workflow during `init`, and takes the Claude Code plugin from GitHub at the tag `v<version>` (ADR-20261011-a9f3, ADR-20261023-7d41).

## Decision

1. **Version `0.1.0`** in `pyproject.toml`, `seamspec/__init__.py` and the plugin's `plugin.json` (and `uv.lock`). The owner's go-ahead for this release step: "start step 5" (2026-10-27). Publishing stays step 6 and needs its own go-ahead (ADR-20261005-3adc).
2. **Classifiers:** `Development Status :: 3 - Alpha`; Linux and macOS, and Python 3.11 to 3.14, which is what CI tests. No Windows classifier, and no licence classifier (the `License-Expression` field replaces it).
3. **Project URLs:** Homepage, Documentation (getting-started), Source, Issues, Changelog.
4. **`CHANGELOG.md`** in the Keep a Changelog format. The 0.1.0 entry says what the release contains and its known limits. Its date is "Unreleased" until step 6 sets the publish date.
5. **The README and getting-started install with `uv tool install seamspec`,** and say how to upgrade. Installing a clone is in `CONTRIBUTING.md`, for unreleased changes. Getting-started says the CI workflow pins the version that wrote it.
6. **The README's links are absolute,** to `https://github.com/seamspec/seamspec/blob/main/…`.
7. **The plugin's start script** gives `uv tool install seamspec` first, then the checkout install.
8. **Tests** (`tests/test_packaging.py`): pyproject and `__version__` always agree; for a release the plugin agrees too, and `CHANGELOG.md` has an entry for it. The README has no relative links.

**Alternatives considered:**
- *README links to the `v0.1.0` tag instead of `main`:* the PyPI page would match the release exactly, but the links 404 until the tag exists (step 6), and docs fixes made after the release wouldn't reach PyPI readers.
- *Keep `0.1.0.dev0` until the publish day:* then step 6 is also a code change to review, and the release behavior (pinned CI, plugin from the tag) is never seen in CI before publishing.

## Enforced Invariants

None new. `tests/test_packaging.py::test_one_version_everywhere` and `::test_readme_links_work_on_pypi` cover points 1 and 6.

## Consequences

- **Between this merge and step 6** (the publish), `main` describes a package PyPI doesn't have yet: `uv tool install seamspec` still gets the placeholder, and SeamSpec installed from `main` (not a checkout) pins CI to `seamspec==0.1.0` and asks for the plugin at `v0.1.0`, neither of which exists yet. A checkout (editable install) is unaffected: it uses itself for the plugin. Keeping the gap short is the remedy; merging step 5 shortly before step 6 is best.
- The next development version (after the release) needs the version bumped in the same three places; the test fails if they disagree.
- Step 6 sets the changelog's date.
